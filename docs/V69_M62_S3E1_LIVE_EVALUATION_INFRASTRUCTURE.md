## Durable identity correction

`ModelIdentity.identity_hash` covered the whole record. Three of its fields say nothing
about which weights load: `cache_status` and `cache_evidence` are **host state**, and
`license_reference` is **documentation**. The same model bytes therefore hashed
differently depending on where the operator keeps their cache and how they worded a
licence note — and `pairing_blockers` compares that digest.

This was not theoretical. Measured against the real artefacts:

| Description of the same Qwen3-0.6B commit | `identity_hash` |
|---|---|
| As run-004 recorded it (cache probed, empty licence) | `9701f4f3…` |
| Same bytes, cache not probed | `28d79d51…` |
| Same bytes, template's licence sentence | `23bc5787…` |

The shipped template writes `"license_reference": "see the model card on the hub"`, so a
baseline derived from it could not pair with the adapter trained on exactly those weights.

**The correction is additive, so nothing already on disk is invalidated.**

- `identity_hash` is untouched, and a test pins that it *still moves* under an annotation
  — every adapter manifest was written against that behaviour.
- `canonical_identity_fields` / `canonical_identity_hash` bind only what an execution
  resolves: model id, immutable revision, tokenizer id, tokenizer revision, remote-code
  policy. Versioned separately as `m62.model_identity.canonical.1`, so the two digests can
  never be confused.
- `parameters_b` and `family` are excluded deliberately: the commit sha already pins
  `config.json`, so a declared parameter count is an operator's *description* of the
  model, not a fact about it.

### Legacy adapter compatibility

`reference_from_manifest` **re-derives** the canonical digest from the manifest's own
`base_model_id`, `base_model_revision`, `tokenizer_id` and `tokenizer_revision` rather
than reading a stored one. That is the whole compatibility bridge: a manifest written
before this authority existed is upgraded by recomputation, never by rewriting the file.
Both digests travel side by side on both references.

`pairing_blockers` compares canonically when both sides carry it, and falls back to the
stricter legacy digest when either does not. **Absent is never "matches."**

Verified against run-004: legacy digests mismatch, canonical digests agree, pair clean;
a different base model is still refused.

## Dependency-gate correction

`DependencyReport.ready` is `all(...)` over `method_packages`, filled from a
`TrainingMethod`. An evaluation has no training method — it selects a *backend* — so all
three call sites passed nothing, the tuple was empty, `all(())` is `True`, and the gate
could not fail on a host with no torch, transformers or peft.

- An empty requirement is now **refused rather than satisfied**: a gate asked no question
  cannot be passed.
- `build_dependency_report` accepts `required_packages` for callers with no method,
  composing with and de-duplicating against a method's own.
- `backends.backend_required_packages` declares what the evaluation path resolves —
  `torch`, `transformers`, `peft`, `safetensors` — and **refuses an unknown backend**
  rather than returning `()`, which would restore the defect through the back door. It
  lives under `backends/` so the purity scan over `evaluation/` keeps holding.
- The CLI routes every request through one helper that cannot omit the argument; an AST
  test fails if any call site drops it.
- A missing package is a **plan blocker**, not a warning.

Verified: on the interpreter running the suite the gate reports `ready=false` and names
`peft`; in `.venv-training-smoke`, where a live run would happen, `ready=true`, no
blockers. Nothing is imported or installed to answer either.

## Held-out corpus

### Two structural blockers found this session

The authority chain **could not express evaluation-only material at all**:

1. `build_candidate` hard-coded `evaluation_only=False` / `dataset_eligible=True` into
   every record, and `candidate_blockers` refused an `evaluation_only` spec outright.
2. `plan_splits` dropped every evaluation-only candidate *before* assignment, so no such
   record could reach a split, a manifest or a version.
3. `Episode.approval_blockers` additionally refused to approve an evaluation-only task,
   although `Episode.outcome()` already derives dataset eligibility separately.

All three conflated "approved evidence" with "training material". They are now separated:
approval says the run is sound; eligibility is decided independently and still refuses
evaluation-only material everywhere it matters. Evaluation-only candidates participate in
splitting **only** when an operator names a destination for their group, and the existing
rule that an override may never name a train-side split covers the rest. A backstop
refuses the outcome itself, because groups merge transitively through shared fixtures and
a forced key can stop matching.

### The corpus

`scripts/build_evaluation_corpus.py` walks 36 synthetic defensive tasks through the full
chain — no hand-written manifest, no invented hash:

```
TaskSpec → Trajectory → approved Episode → deterministic aggregation → teacher consensus
→ DatasetHumanReview → DatasetCandidate → SplitPlan → LeakageReport → PromotionPlan
→ PROMOTE:<plan-hash> → immutable DatasetVersion
```

| | |
|---|---|
| Dataset | `m62-defensive-eval` `v1` |
| Candidates built / promoted / rejected | 36 / 36 / 0 |
| Splits | `hidden_evaluation` 12, `security_regression` 12, `adversarial` 12 |
| Families | `safety_refusal` 12, `structured_report` 9, `evidence_request` 9, `tool_call_schema` 6 |
| Decision classes | `required_refusal` 12, `required_completion` 6, `completion` 18 |
| Leakage | **CLEAN**, 0 findings |
| Manifest hash | `0970600c677c89112db972c6024634aa871be92dee303db7f429c90967d3dd3b` |

Generated bytes are gitignored and package-excluded; only the generator is tracked.

### Two deliberate deviations from the requested shape

**No VALIDATION material.** The session brief asked for 8–10 VALIDATION tasks.
`TRAIN_SIDE_SPLITS = {TRAIN, VALIDATION}`: a model is *steered* on VALIDATION, and three
independent authorities refuse evaluation-only records there. Held-out evidence a model
was steered on measures nothing, so weakening that control to hit a split count would
defeat the corpus's own purpose. The corpus occupies the three genuinely held-out splits.

**Records are `INTERNAL`, not `SYNTHETIC`.** The leakage analyser warns that
teacher-exportable held-out material can have its expected answer placed in a teacher
packet. It is right to. The sensitivity class was corrected rather than the warning
suppressed — this removed all 36 findings by making the material genuinely non-exportable.

**Family mapping note.** The brief lists `adversarial` as a mandatory *family*. This
repository models adversarial as a **split**, not a family, and has no `ADVERSARIAL`
member of `TaskFamily`. Adversarial coverage is therefore the 12-task `ADVERSARIAL`
split, spanning all four families. `evidence_grounding` maps to `TaskFamily.EVIDENCE_REQUEST`.

## Dataset-to-task-pack builder

`training_gym/evaluation/pack_builder.py` :: `build_task_pack_from_dataset` reads a
promoted, hash-verified `DatasetVersion` and returns a `BuiltPack` carrying the
model-facing pack **and** the hidden-target store together, so neither can be obtained
without the other.

`load_manifest` is the only loader used — it re-hashes every shard from disk, refuses
symlinks and hard links, and re-derives each record's digest. No second, weaker opinion
about integrity is added.

**Refuses:** `TRAIN` unconditionally, `QUARANTINE`, unknown or repeated splits, any record
not `PROMOTED`, duplicate task ids, records with no prompt or no expected answer, families
with no grader or schema mapping, and any schema that names the answer.

**Hidden-target isolation.** The builder is the last place an answer can escape, because
it chooses the graders, the response schema and the tool definitions. Response schemas are
therefore structural and empty of content — a schema listing the permitted values of a
verdict field has published the answer key under a heading. Every finished task is
re-checked for exposure after all mapping decisions. The store is frozen before return and
exports digests only.

**Mappings** are deterministic per family: graders (`secret_pii` mandatory everywhere),
one response schema, tool schemas only where a tool call is asked for. Tasks are ordered
by `(task_hash, task_id)`, so the pack hash does not depend on the order splits were named.

`pack_blockers` is separate from construction: a pack too small to support a claim is
still legitimate to run and look at; what it may not do is decide.

## Live execution wiring

`training_gym/evaluation/execution.py` :: `execute_evaluation` is the caller the pipeline
never had. It invents no scoring, writes no artifact format and reaches no verdict. What
it adds is **order**:

1. refuse a blocked plan or an already-consumed one — nothing spent;
2. create the generation directory (`mkdir(exist_ok=False)` — the mutual exclusion) **before**
   spending the plan, so a lost race spends nothing;
3. consume the plan;
4. build and verify the task pack from the promoted dataset;
5. construct **two separate** backend objects, refusing a shared one;
6. run the paired evaluation, score, compare, gate, report;
7. write artefacts, then re-verify them from disk;
8. `COMPLETED` — written by exactly one line, only after step 7 passed.

### State machine

`preflight_verified → starting → running_baseline → running_candidate → scoring →
comparing → artifact_validation → completed`, every move checked against the existing
`ALLOWED_EVALUATION_TRANSITIONS`. Failure routes to `failed`; artefact-validation failure
to `quarantined`; `KeyboardInterrupt` to `interrupted`. No exception can leave a run
`RUNNING`, every terminal outcome appends a ledger line, and a failed generation is moved
to quarantine rather than left in place.

### Fairness

Both arms receive the same pack, the same order policy, the same tokenizer identity, the
same generation policy, the same graders, schemas and tool definitions. The only permitted
difference is that the candidate has the verified adapter attached — enforced structurally
by the two-object rule, not asserted.

### Registry boundary

Nothing here writes the production registry, promotes, activates, assigns a role or merges
an adapter. `MODEL_REGISTRY_PROPOSAL: NOT_CREATED`.

## Synthetic qualification

52 scenarios drive the **real** execution path with deterministic doubles against the real
36-task corpus. This is safe because `classify_empirical_status` reads the backend ids that
actually answered and marks anything synthetic `SYNTHETIC_ONLY`, which `decide_eligibility`
refuses **before** it looks at a single gate. A fake run therefore produces a complete,
honest report that can never conclude an adapter is eligible.

Honest outcomes confirmed:

- a critical security failure vetoes, and is not traded against a quality improvement;
- a candidate that refuses everything does **not** win — the reason the corpus carries
  required-completion tasks;
- missing pairs, timeouts and both-arms-failing stay visible as *unmeasured*, never as
  losses; a zero denominator is `None`, not `1.0`;
- a below-minimum pack still runs and still cannot make a directional claim;
- a missing mandatory split or family is a blocker;
- a replayed plan, duplicate generation, stale or malformed token, shared backend object
  and blocked plan are each refused before anything is spent;
- artefacts that do not verify quarantine the generation and never reach `completed`;
- an interruption is terminal, honest, and still spends the plan.

**Infrastructure qualification is not adapter-quality evidence.** These numbers describe
test doubles.

## Limitations

- The adapter's quality is **not measured**. `EMPIRICAL_STATUS: NOT_MEASURED`.
- Every gate threshold remains an initial policy value, uncalibrated against any measured
  distribution.
- The corpus is synthetic and bounded. 36 tasks clears `min_pairs_for_claim`, but clearing
  a minimum is not the same as being a representative sample of defensive work.
- The corpus was authored in one session by one author; it has no independent review.
- `VALIDATION` carries no evaluation-only material, by policy (see above).
- The live path has never executed. Its structure is qualified; its behaviour under a real
  transformers/peft load is not.
