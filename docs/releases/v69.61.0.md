# JARVIS v69.61.0 — Production Stabilization, CI & Release Engineering

**Canonical version:** `69.61.0` (`jarvis/core/version.py` — the single authority)
**Release kind:** stabilization. No new agent, model, security subsystem or autonomous
capability.
**Merge commit:** `0bb1a6b` — *merge: JARVIS V69 M61 production stabilization and release
engineering* (PR #2)
**Closure stage:** M61.8, Release Closure & Verifiable Release Evidence. M61.8 is an
internal stage of this release, **not** a version.

> This is a **local-first, operator-controlled, security-focused** homelab release. It is
> **experimental** software for the operator's own systems, an isolated lab, CTFs and
> defensive work. It is **reproducibly qualified**: every number below has a command
> beside it. It is **not** an enterprise or production-certified product, it makes no
> availability or support commitment, and **optional live validation was not executed for
> this release** — see [Live validation](#live-validation).

---

## Summary

M52–M60 built capability faster than the repository's *engineering surface* could keep
up. The result was a codebase whose runtime was well tested and whose packaging,
versioning, dependency story and documentation were not tested at all: package metadata
sat at `63.0.0` six milestones late, the project had never been built, the DEBUG log went
to a CWD-relative path, the boot sequence ran `pip install --break-system-packages` on
the operator's host unasked, and the CI audit gate ended in `|| true`.

None of that is fixed by adding a subsystem. Every change in this release either
establishes a source of truth, verifies an existing claim, or removes an unrequested side
effect — and M61.7 fixed 29 real static-analysis findings, several of which were
genuine vulnerabilities rather than lint.

## Scope

**In scope:** version authority, documentation truth, CI, dependency authority, managed
logging and paths, packaging, silent-failure correction, release qualification and soak,
static-analysis remediation, and (M61.8) reproducible release evidence, checksums, SBOM,
dependency policy, release notes and a guarded release procedure.

**Out of scope:** new capability of any kind, structural refactoring (`main.py` is
untouched beyond two exception classifications and the logging sink), and eliminating the
488 Low-severity static-analysis findings.

## What changed

### Canonical version authority (M61.1)

`jarvis/core/version.py` is the single source. `pyproject.toml` derives from it as dynamic
metadata; the runtime, diagnostics, release qualification, packaging and the documentation
all derive from or are verified against it. Package metadata had been stuck at `63.0.0`.

### Documentation truth (M61.1 / M61.8)

`core/release_check.py` is a deterministic scanner over the repository's own files — it
reads, never writes, and never executes what it reads. Nine checks in eight families:
version derivation, model-role claims, autonomy claims, release status, README install
commands, and (M61.8) validated counts, the static-analysis result, the declared security
postures and a release-state check that refuses both a merged milestone documented as
unmerged **and** a tag or GitHub Release claimed before it exists.

Corrections this release: the claim that JARVIS is "a complete autonomous Purple Team
security platform" that "attacks autonomously" (every offensive path is behind HITL/NATO
approval plus the trusted-lab flag); the superseded `qwen2.5 7B/14B` role claim; four
release documents that denied merges that had landed; and a hardware-tier table still
recommending five models retired in V66.1, under a sentence promising it was what
`model_doctor.py` prints.

### Crash-safe session continuity (carried from V69 M60, verified here)

A versioned session/turn/run journal on the durable operational store. After an unclean
exit the runtime reconciles interrupted turns, and **reconciliation has no execution
path**, so a recovered session never replays an effectful action. The deterministic soak
drives that spine — including an interrupted turn and an unfinished effectful tool
operation — and `actions_replayed` is structurally `0` in every cycle.

### Managed logging and paths (M61.4)

The DEBUG file sink was `logger.add("jarvis.log", …)` — a CWD-relative string, producing
one 2.7 MB log per directory the app had been launched from. It now resolves absolutely
through `core.managed_paths`, declares rotation (10 MB) and retention (7 days) once
instead of duplicating the literals at two call sites, and **redacts on the way to
disk**, so an OTP, a credential-shaped token or the operator's home path cannot reach the
log file even if a call site formats one into a message. The filter rewrites the message;
it never drops the record.

Two continuity modules also created a directory at *import* time — a side effect that
fired inside test collection and packaging tools. Proven fixed: a subprocess launched with
a temp directory as its CWD, importing those modules and `main`, leaves it empty.

### Packaging (M61.5)

The project had never been built, so it was undiscovered that it could not be: the flat
layout is exactly the shape setuptools auto-discovery refuses. The layout, package data
and exclusions are now declared, `MANIFEST.in` prunes what a developer tree actually
carries, and `scripts/check_package_manifest.py` does not trust either — it opens the
built wheel and sdist and inspects the real member list from the archive index.

`__main__.py` is deliberately not packaged: installing a top-level `__main__` into
site-packages would put it on every other program's path.

### CI (M61.2 / M61.7)

`.github/workflows/ci.yml` — seven mandatory jobs and exactly one advisory step, whose
result stays visible. No mandatory gate uses `|| true` or `continue-on-error`. CI needs no
Ollama, model, microphone, TTS hardware, Docker daemon, Redis, PostgreSQL, API key,
trusted-lab mode or elevation.

### Dependency authority (M61.3)

`jarvis/requirements/<profile>.txt` is the declared authority; `pyproject.toml` mirrors it
and is verified byte-for-byte as a mandatory gate. Real drift was found and fixed: the
`soc` extra was missing eight packages the profile installs and `lab` was missing seven,
so `pip install jarvis[soc]` and `pip install -r requirements/soc.txt` produced different
environments.

Boot-time dependency installation is **report-only** unless the operator sets
`JARVIS_AUTO_INSTALL_DEPS=true`, and `--break-system-packages` is gone entirely.

### Static-analysis remediation (M61.7)

The blocking gate reported **29 findings: 21 Medium and 8 High**. It now reports
**0 Medium and 0 High**, with the command and threshold unchanged — the findings were
fixed, not the gate. Four were more than lint:

- **Dynamic plugin execution is refused, fail-closed.** `core/plugin_loader.py` claimed
  cryptographically-verified plugins, a signed manifest and a restricted `exec`
  environment. All four claims were false: an `exec` globals dict with trimmed
  `__builtins__` restricts a *namespace*, not privileges, and three lines inside the
  "sandbox" were verified to import `os`, read arbitrary files and spawn a subprocess.
  The manifest hash was never a signature, and hot-reload meant a dropped file ran with
  no operator approval. This release takes the smallest safe option — refuse to execute —
  with **no environment variable to re-enable it**, because an opt-in flag is the same
  vulnerability behind a different default. **There is no plugin sandbox and this release
  does not claim one.** Manifest parsing, integrity verification and reporting are intact,
  and refusals stay visible so a dashboard cannot show "0 plugins" and leave an operator
  believing the directory was empty.
- **SSH host-key verification is enforced.** `AutoAddPolicy()` is trust-on-first-use with
  nobody in the loop: on the flat lab networks these bridges point at, the first machine
  to answer became permanently trusted and was authenticated with the operator's own
  private key. `core/ssh_policy.py` is fail-closed with `RejectPolicy` and a two-step
  operator enrollment. Automated remote sensor deployment is off by default and returns
  an action plan; the opt-in stages a file to a unique 128-bit, `0600`, home-relative path
  and never installs or starts anything remotely.
- **XML and URL hardening.** Sysmon telemetry now parses through `defusedxml` with no
  ElementTree fallback and explicit input size bounds. `urlopen` is not an HTTP function —
  its default opener also serves `file:`, `ftp:` and `data:`, so a `file:///` value in a
  `.env` made the health probe report a read local file as "responsive" and made network
  **containment** report success while the host stayed on the network. `core/url_policy.py`
  enforces a scheme allowlist, refuses credentials in URLs, and **re-validates every
  redirect hop**, because the stdlib redirect handler will follow a 302 into `ftp:`.
- **Loopback-first network defaults.** Four services bound all interfaces with no gate, so
  starting JARVIS on a laptop published decoy SSH/SMB/RDP/MSSQL listeners and a DNS
  resolver to whatever network that laptop was on. `core/net_binding.resolve_bind_host`
  generalises the already-correct canary pattern: loopback default, per-service
  `JARVIS_<SERVICE>_EXPOSE` opt-in, an operator-named single address honoured as the
  narrower option, and a WARNING naming the service and the proven bind address on every
  exposure. The safe default logs nothing, so the warning still means something.

Also fixed: unsafe non-cryptographic hashes where a security decision read them, and a
real U+200F right-to-left mark embedded in the anti-Trojan-Source module's own
translation table — a file whose rendered text could disagree with what the interpreter
executes.

### Release evidence, checksums and SBOM (M61.8)

`jarvis/scripts/build_release_evidence_m61.py` emits a sanitized, schema-validated
`release-evidence.json` plus `SHA256SUMS` and one CycloneDX 1.5 SBOM per dependency
profile. A missing mandatory result becomes `INSUFFICIENT_EVIDENCE`, never a pass; the
write is atomic; and the bundle carries no absolute path, username, hostname, environment
value, credential, prompt, conversation, log or database.

### About the pass/skip totals

The count is **environment-dependent, legitimately**: a suite whose optional dependency is
absent collapses into a single module-level skip instead of contributing N passing tests,
so a leaner environment reports fewer of both. The totals above were measured on
`python3.12 / windows-amd64` with the `dev`, `soc` and `lab` profiles installed, and that
context is part of the claim. CI's authoritative Python 3.11 job installs `dev`+`soc` and
will report a different split for the same reason — that is expected, not drift.

The claim that is environment-independent, and the one this release rests on, is
**0 failures in both supported layouts**.

### Release qualification verdict

`PASS_WITH_WARNINGS`, with exactly one warning: `live_not_requested`.

This is reported honestly and is **not** rounded up to `PASS`. Every mandatory gate is
green; the warning records that optional live validation was not part of this evidence
set.

### Live validation

**Status: `NOT_REQUESTED` — optional live validation was not executed for this release.**

`qualify_release_m61.py --live` adds a bounded, safe live smoke: Ollama reachability, one
deterministic time bypass that makes no model call, and runtime-log placement. It never
downloads a model, restarts or configures the server, runs an offensive tool, scans a
network or touches host settings. A host without Ollama yields `INSUFFICIENT_EVIDENCE` —
never a false pass and never a false failure, because a service-free host is a supported
configuration.

No claim is made here that live inference, voice mode, Windows-live or Linux-live
operation was demonstrated for this release.

## Installation

Requires **Python 3.11+**. Verify the artifacts before installing.

```bash
# from the release directory, after downloading the artifacts and SHA256SUMS
sha256sum -c SHA256SUMS            # Linux/macOS
# Windows PowerShell:
#   Get-FileHash .\jarvis-69.61.0-py3-none-any.whl -Algorithm SHA256

python -m pip install ./jarvis-69.61.0-py3-none-any.whl          # text mode floor
python -m pip install "./jarvis-69.61.0-py3-none-any.whl[soc]"   # + defensive SOC/DFIR
```

From a source checkout, the profile installers are the supported path:

```bash
cd jarvis
./scripts/install.ps1                 # Windows; -Profile all for everything
./scripts/install.sh                  # Linux/macOS; ./scripts/install.sh all
python scripts/doctor.py              # PASS/WARN/FAIL environment check
python main.py                        # text mode (or: python -m jarvis)
```

`lab` is offensive-capable and is for an isolated, authorized lab only. It is never
installed by `base`.

### Verifying this release

```bash
# artifacts
sha256sum -c SHA256SUMS

# SBOM (regenerate and compare, or validate what was published)
python jarvis/scripts/build_sbom.py --validate <release-dir>

# evidence bundle — validates against the schema published beside it
python -c "import json,sys; sys.path.insert(0,'jarvis'); \
from core.release_evidence import validate_evidence; \
print(validate_evidence(json.load(open('release-evidence.json'))) or 'OK')"

# reproduce the gates yourself
python jarvis/scripts/check_release_consistency.py
python -m pytest -q jarvis/tests tests
cd jarvis && bandit -r core tools -ll -q && cd ..
python jarvis/scripts/qualify_release_m61.py --full
```

### SBOM

CycloneDX 1.5 JSON, one document per dependency profile (`base`, `dev`, `soc` in the
release bundle; `voice`, `docs`, `lab` on request):

```bash
python jarvis/scripts/build_sbom.py --output <dir>
python jarvis/scripts/build_sbom.py --output <dir> --profiles base,dev,soc,voice,docs,lab
```

Generation is offline and byte-reproducible: same tree, identical bytes. The documents are
**declared-authority** SBOMs and say so in their own metadata — they enumerate direct and
inherited declarations from the dependency authority and do **not** resolve the transitive
installation closure, which would need a live resolver and a fixed platform.

## Upgrade notes

- **No migration is required.** No on-disk format, database schema, journal version or
  configuration key changed in this release.
- **Package metadata jumps from `63.0.0` to `69.61.0`.** The old number was six
  milestones stale, not a downgrade of anything.
- **`jarvis/requirements.txt` is a deprecated pointer.** Use
  `requirements/<profile>.txt`, or the `pyproject.toml` extras — they are now verified
  equivalent.
- **`pip install jarvis[soc]` and `pip install jarvis[lab]` now install more than
  before**, because the extras were missing packages their profiles install. That is the
  drift being corrected, not new dependencies being added.
- **Boot no longer installs packages on your host.** If you relied on that, set
  `JARVIS_AUTO_INSTALL_DEPS=true` explicitly. `--break-system-packages` is not passed
  under any setting.
- **Drop-in source plugins no longer execute.** Manifest parsing, integrity verification
  and reporting still work, and refusals are reported rather than counted as zero
  plugins. There is no flag to restore execution.
- **Services that previously published to your whole network no longer do.** If you
  intentionally exposed the decoy, tarpit, active-tarpit or DNS-sinkhole services, set
  that service's `JARVIS_<SERVICE>_EXPOSE` variable. Every exposure logs a WARNING naming
  the service and the address.
- **SSH bridges refuse unknown hosts.** Enroll host keys through the documented two-step
  operator action; trust-on-first-use is gone.
- **The DEBUG log moved** out of the launch directory into the managed application tree
  and is now redacted before it reaches disk. Old `jarvis.log` files in old working
  directories are safe to delete.

## Security invariants

Unchanged and re-verified by the M52–M60 regression suites: `ToolExecutor`, `Authority`,
`ScopePolicy`, risk classification, HITL/NATO approval, audit logging, the
prompt-injection firewall, content trust labelling, SSRF protection, path
canonicalization, crash reconciliation, the no-replay-of-effectful-actions guarantee,
trusted-lab gating and secret redaction.

Nothing was introduced from the forbidden set: no `shell=True`, no `os.system`, no
`eval`/`exec`, no arbitrary command templates, no model-supplied file paths, no global
keyboard hooks, no Windows service, scheduled task or startup entry, and no automatic
remote installation.

Three things moved in the safer direction: host dependency installation is off by
default, the runtime log is redacted before it reaches disk, and SSH host keys are
verified. The declared postures are enumerated in
[SECURITY.md](https://github.com/alejandrobalsas26-sys/jarvis/blob/master/SECURITY.md).

## Known limitations

1. **Optional live validation was not executed** for this release (`NOT_REQUESTED`). No
   live-inference, voice, Windows-live or Linux-live claim is made.
2. **488 Low static-analysis findings remain**, recorded as an enforced baseline rather
   than eliminated or called harmless. See
   [`docs/DEPENDENCY_SECURITY_POLICY.md`](../DEPENDENCY_SECURITY_POLICY.md) §5.
3. **The advisory `pip-audit` result is not triaged.** This release makes it visible;
   acting on it is separate work, and it is the highest-value item for the next pass.
4. **There is no plugin sandbox.** Dynamic source-plugin execution is refused
   fail-closed. That is a removal, not a sandbox.
5. **One legacy security test is CWD-sensitive.** `tests/test_security.py`'s relative
   traversal case resolves its fixture against the working directory, so the two supported
   layouts exercise different paths. The root-layout invocation is authoritative and is
   what CI and the qualification use; fixing the test means touching a security path,
   which a stabilization release should not do opportunistically.
6. **~24 modules still resolve `logs/…` against the CWD** and 12 still `mkdir` at import.
   Bounded, AST-inventoried and pinned by ceiling tests so the exposure cannot grow.
7. **Base-install purity is proven in CI, not locally.** A development machine has every
   profile installed, so the local check is necessary and not sufficient.
8. **The transitive dependency closure is not resolved** in the SBOM.
9. **`main.py` is still ~3,300 lines.** No extraction was performed; a structural split
   needs its own milestone with its own tests.
10. **macOS is untested.** No claim either way.

## Rollback

This release changes no on-disk format, so rollback is a reinstall — there is nothing to
migrate back.

```bash
# installed from a wheel
python -m pip install --force-reinstall jarvis==<previous-version>

# from a source checkout
git checkout df35289          # V69 M60, the release this one builds on
cd jarvis && pip install -r requirements/<profile>.txt
```

If you rolled back because of a behaviour change rather than a defect, the four
likely causes are all opt-outs rather than reverts, and are safer than rolling back:

| Symptom | Instead of rolling back |
|---|---|
| a service is no longer reachable from the network | set that service's `JARVIS_<SERVICE>_EXPOSE` |
| boot no longer installs a missing package | set `JARVIS_AUTO_INSTALL_DEPS=true` |
| an SSH bridge refuses a host | enroll the host key (two-step operator action) |
| a drop-in plugin no longer runs | no opt-out exists by design — port the plugin to a first-class tool |

State written by this release (journals, session snapshots, the managed log tree) is
readable by V69 M60: no journal or snapshot version was incremented.
